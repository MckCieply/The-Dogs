# AUTH-05 — Password reset (admin-token flow, no SMTP)

## Summary

Adds the forgotten-password flow per [ADR-0013](../adr/0013-password-reset-without-smtp.md). Because the project has no SMTP, tokens are not emailed — they are generated by `POST /auth/forgot-password`, retrieved by an admin via `GET /api/v1/admin/password-reset-tokens?email=...`, and used by the end user via `POST /auth/reset-password`. Anti-enumeration: `forgot-password` always returns `204` regardless of email existence. The same password strength validator from `AUTH-04` enforces the new password.

## Motivation

- Users will forget passwords. Without a reset path the only recovery is manual DB hand-editing.
- The admin-token bridge is operationally acceptable at zero/early users and migrates to real email later by swapping only the delivery channel ([ADR-0013](../adr/0013-password-reset-without-smtp.md)).
- All token plumbing (table, hashing, expiry, single-use) lands now so that when SMTP is added the only change is the delivery code path.

## Scope

### In scope
- Flyway migration creating `password_reset_token` table.
- `POST /api/v1/auth/forgot-password { email }` — always returns `204`, creates a token row if the email exists.
- `POST /api/v1/auth/reset-password { token, new_password }` — verifies token, updates password, marks token used.
- `GET /api/v1/admin/password-reset-tokens?email=...` — `ROLE_ADMIN` only, returns the active token for the given email or `404` if none exists.
- Optional dev-mode helper: `INFO` log line on token creation with the token value, gated by `app.password-reset.log-token-on-create` (default `false` in prod, `true` in dev profile).
- Revoking all of the user's refresh tokens on successful password reset (so any active sessions are forcibly logged out).
- Rate limit: 3 forgot-password requests per email per hour (key the bucket by `email_hash` so the bucket exists even for non-existent emails — keeps the enumeration timing flat). 10 reset-password attempts per IP per hour.
- Integration tests across the full flow.

### Out of scope
- Email delivery (any form) — explicitly deferred per [ADR-0013](../adr/0013-password-reset-without-smtp.md).
- Security questions / out-of-band fallback identity verification.
- Self-service "change password while logged in" flow — separate spec (`profile-page` or a dedicated `change-password`).
- Notification on password change ("Your password was changed" email) — depends on SMTP.

## Acceptance criteria

- AC-1: `POST /auth/forgot-password` with a known email returns `204`. Exactly one row is inserted in `password_reset_token` with `expires_at = now() + 1 hour`, `used_at IS NULL`.
- AC-2: `POST /auth/forgot-password` with an unknown email returns `204`. No row is inserted. Response timing is within ±20% of the known-email case (asserted by a coarse timing test — the bucket lookup runs either way, plus a constant-time delay to absorb DB roundtrip variance).
- AC-3: `GET /admin/password-reset-tokens?email=...` as `ROLE_ADMIN` returns `200` with `{ "token": "<value>", "expires_at": "..." }` for an active token, or `404` if no active token exists.
- AC-4: `GET /admin/password-reset-tokens` as `ROLE_TRAINER` returns `403` `errors[].code = "forbidden"`.
- AC-5: `POST /auth/reset-password` with a valid token + strong new password returns `204`, updates `app_user.password_hash`, marks the token `used_at = now()`, and revokes every active row in `refresh_token` for the user.
- AC-6: After AC-5, the user can `POST /auth/login` with the new password. The old password is rejected.
- AC-7: After AC-5, every previously issued refresh token for the user returns `401 refresh_revoked` on `/auth/refresh`.
- AC-8: Reusing a `used_at IS NOT NULL` token returns `400` `errors[].code = "invalid_reset_token"`.
- AC-9: An expired token (past `expires_at`) returns `400` `errors[].code = "invalid_reset_token"`. Same code as AC-8 — clients should not distinguish.
- AC-10: A weak new password returns `400` `errors[].code = "password_too_weak"` + `password_score`, identical to `AUTH-04` semantics.
- AC-11: 4th `forgot-password` from the same email-hash in an hour returns `429 too_many_attempts`. Anti-enumeration preserved by bucketing on `email_hash`, so non-existent emails get the same throttle.
- AC-12: In the test profile, the token value is captured from the log (asserted) — proving the dev helper works without leaking in prod. The prod profile asserts the helper is **off** and the token does not appear in logs.
- AC-13: `mvn verify` exits 0; OpenAPI snapshot regenerated. New error codes `invalid_reset_token` added to `docs/api/error-codes.md`.

## Investigation notes (for the implementer)

- Token value: 256 random bits, base64url-encoded. DB stores SHA-256 hash, same pattern as `refresh_token`.
- `forgot-password` flow on unknown email: still spend the same wall-clock as the known path. Easiest implementation: always rate-limit lookup + always run a fixed delay (`Thread.sleep(50)`) when unknown. Document the trade-off (`Thread.sleep` is acceptable on a virtual-thread executor; on platform threads it would burn one).
- Admin endpoint `/admin/password-reset-tokens` is the only place a token value ever leaves the backend through a non-cookie path. Reviewer must verify it is gated by `@PreAuthorize("hasRole('ADMIN')")` at the **service** layer and that the controller method is annotated as well (belt-and-braces).
- Revoking the user's refresh tokens on reset: one `UPDATE refresh_token SET revoked_at = now() WHERE user_id = ? AND revoked_at IS NULL` statement. Cleaner than iterating.
- For the dev-mode log helper: do not just `log.info("Token: " + token)` — use SLF4J structured logging with an MDC marker `reset-token-dev` so it can be grepped/scrubbed if it accidentally lands in shipping logs.

## Data model

### `password_reset_token` table

```sql
CREATE TABLE password_reset_token (
    id          UUID PRIMARY KEY,
    user_id     UUID NOT NULL REFERENCES app_user(id) ON DELETE CASCADE,
    token_hash  CHAR(64) NOT NULL UNIQUE,
    issued_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    expires_at  TIMESTAMPTZ NOT NULL,
    used_at     TIMESTAMPTZ,
    requested_ip_bucket TEXT
);

CREATE INDEX idx_password_reset_token_hash ON password_reset_token (token_hash);
CREATE INDEX idx_password_reset_token_user_active
    ON password_reset_token (user_id) WHERE used_at IS NULL;
```

Only one active token per user is allowed at a time: a second `forgot-password` for the same user during the validity window **revokes** the previous (marks `used_at = now()`) and issues a new one. Documented in the migration comment.

## API surface

| Method | Path                                       | Auth          | Body                          | Response |
| ------ | ------------------------------------------ | ------------- | ----------------------------- | -------- |
| POST   | `/api/v1/auth/forgot-password`             | `permitAll`   | `{ "email": "..." }`          | `204` always (anti-enumeration). |
| POST   | `/api/v1/auth/reset-password`              | `permitAll`   | `{ "token": "...", "new_password": "..." }` | `204` on success, `400` for invalid/expired/used token or weak password. |
| GET    | `/api/v1/admin/password-reset-tokens`      | `ROLE_ADMIN`  | query `?email=...`            | `200 { token, expires_at }` or `404`. |

## UI surface

None. `AUTH-08` is the matching frontend spec for end-user flows; admin retrieval is exposed via existing admin tooling (curl / future admin UI).

## Security & RBAC

- Tokens hashed at rest (SHA-256 of the random 256-bit value).
- Admin endpoint locked to `ROLE_ADMIN` at service layer.
- Anti-enumeration: identical response shape and equal timing for known vs. unknown email on `forgot-password`.
- Password strength enforced by the same validator as `AUTH-04`.
- Successful reset revokes every active refresh token for the user (forced logout of all sessions).
- Single active token per user — preventing token-piling attacks.
- Reviewer enforces: no log line contains the raw token, no admin-token retrieval happens without an admin-role check.

## Non-functional

- p95 latency for `reset-password` ≤ 250 ms (bcrypt cost 12 + DB writes).
- `forgot-password` constant-time floor ≥ 80 ms regardless of email existence (cumulative DB + fixed sleep).
- Testcontainers integration suite stays under 45 s for this spec's tests.

## Open questions

- **Token TTL.** 1 hour is the default — short enough to limit theft window, long enough for an admin to communicate the value out-of-band. If user complaints arrive, bump to 2 hours via config.
- **Multiple admin-token retrievals.** The current spec returns the token plaintext when an admin requests it — that means the admin sees and could record it. Alternative: admin endpoint returns a one-time-use deep link only viewable once. Deferred — current pattern is acceptable for trusted-admin contexts.
- **Anti-enumeration timing.** A 50ms `Thread.sleep` floor is a blunt instrument. If a security reviewer flags this later, replace with a per-request randomised delay or a more sophisticated approach.
